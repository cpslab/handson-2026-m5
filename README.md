# handson-2026-m5

研究室の新3年生向けハンズオン「**PlatformIO × M5Stack CoreS3 マイコンコーディング回**」の教材・デモ一式です。
複数の講師で開発しています。作業を始める前にこの README を一読してください。

---

## ハンズオンの概要

| 項目 | 内容 |
|---|---|
| 対象 | 研究室に新しく入る3年生 **10人**（マイコン初心者を想定） |
| 時間 | **約200分** |
| 機材 | 各自のPC（PlatformIO は事前インストール済み）、M5Stack **CoreS3**、外付けセンサー（**使用必須**） |
| 最終ゴール | **息を吹き込むと風船が膨らむゲーム**を全員で遊ぶ |

### 風船ゲームのイメージ

1. 各自がチューブに息を吹き込む
2. 大画面（プロジェクター）上で自分の風船が膨らむ
3. 一定以上膨らむと割れる
4. 割れた順に順位を表示する

詳しくは [ゲームのルール](#ゲームのルール親機側の処理) を参照。

---

## 設計方針（重要）

> **子機はできるだけシンプルに、作り込みは親機側（Node-RED・ブラウザ）に寄せる。**

- 子機のコードは **3年生に配布** する。当日は時間がないので、ブロック単位で「何をしているか」を説明する程度にとどめる。
- 子機の役割は **「圧力を測って送るだけ」**。
  - ゲームロジック（しきい値、風船の大きさ、割れ判定、順位）は **子機に入れない**。
  - 理由: しきい値や膨らむ速さを、当日 **親機側だけで一括調整** できるようにするため。
- 3年生が書き換えてよい箇所は **2〜3か所** に絞る（例: 自分の名前、風船の色）。
- 子機のコードは初心者が読める書き方にする。**コメントは日本語**で、ブロックごとに役割を書く。

## システム構成

```
子機 CoreS3 ×10 ──(Wi-Fi)──> MQTTブローカー ──> Node-RED ──(WebSocket)──> ブラウザ表示（プロジェクター）
```

### 通信方式: Wi-Fi + MQTT

- 経路: 子機 → Wi-Fi → MQTTブローカー → Node-RED
- 必要なもの:
  - 専用 Wi-Fi ルーター（**2.4GHz**）
  - MQTT ブローカー（Mosquitto または Node-RED 内の aedes）
- 大学の Wi-Fi（eduroam 等）は使わない。
- SSID・パスワード等は `secrets.h` に分離する（[開発ルール](#開発ルール)参照）。
- トピック:
  - 子機は `handson/balloon/<id>` に送信する
  - Node-RED は `handson/balloon/+` で購読する

### データ形式

- 子機が送る値: **ID（名前）** と **ゼロ点からの圧力差**（＋必要なら色）
- 送信頻度: **1秒に10〜20回** 程度
- ペイロードは JSON:
  ```json
  {"id":"ikai","p":3.2}
  ```
- Node-RED → ブラウザは、全員分をまとめて 1秒に10〜20回程度に間引いて送る（形式は次の節）。

### Node-RED ↔ ブラウザのメッセージ形式（案）

> ⚠️ 案の段階。Node-RED 担当と合意したら「（案）」を外す。

#### 接続先

| 用途 | パス | Node-RED のノード |
|---|---|---|
| 表示画面の HTML | `/balloon/`（末尾の `/` が必要） | `http in` → `http response` |
| CSS・JS など | `/balloon/<ファイル名>` | `http in` → `http response` |
| WebSocket | `/ws/balloon` | `websocket in` / `websocket out`（同じパスを共有） |

- HTML は CSS・JS を相対パスで読み込むため、`/balloon`（`/` なし）で開くと読み込めない。詳しくは [web/README.md](web/README.md) を参照。
- メッセージはすべて JSON で、`type` で種類を区別する。

#### Node-RED → ブラウザ: `state`（ゲームの状態）

ゲームの状態を **まるごと（スナップショット）** 1秒に10〜20回送る。
ブラウザは届いた内容をそのまま描くだけでよく、途中でページを開き直しても次のメッセージで元どおりになる。

```json
{
  "type": "state",
  "phase": "playing",
  "countdown": null,
  "remaining": 42.5,
  "players": [
    { "id": "ikai",   "color": "#ff6699", "level": 0.42, "p": 3.2, "burst": false, "rank": null, "online": true },
    { "id": "tanaka", "color": "#33aaff", "level": 1.0,  "p": 0.1, "burst": true,  "rank": 1,    "online": true }
  ]
}
```

| フィールド | 内容 |
|---|---|
| `phase` | ゲームの段階: `waiting`（待機）/ `countdown`（3・2・1）/ `playing`（計測中）/ `finished`（終了） |
| `countdown` | カウントダウンの残り（3, 2, 1）。`countdown` 以外のときは `null` |
| `remaining` | 制限時間の残り[秒]。`playing` 以外のときは `null` |
| `players` | 参加者の一覧。**配列の順番 = 画面のマスの位置**（Node-RED が接続順で固定する） |
| `players[].id` | 子機の ID（名前） |
| `players[].color` | 風船の色。子機から届かなければ Node-RED が割り当てる |
| `players[].level` | 膨らみ具合。**しきい値に対する割合（0.0〜1.0）**。1.0 で破裂 |
| `players[].p` | 今の圧力[kPa]。待機中に「吹けているか」を確認する表示用 |
| `players[].burst` | 割れたかどうか |
| `players[].rank` | 順位（1〜5）。割れていない、または順位外なら `null` |
| `players[].online` | 通信できているか。一定時間（例: 2秒）データが来なければ `false` |

- `level` を割合で送るのは、**しきい値を Node-RED だけで持つ**ため。ブラウザはしきい値を知らなくてよい。
- 割れる演出は、ブラウザが `burst` が `false` → `true` に変わった瞬間を見つけて再生する。

#### ブラウザ → Node-RED: 操作

| メッセージ | 動作 | 受け付ける段階 |
|---|---|---|
| `{"type":"start"}` | カウントダウンを始め、終わったら計測を開始する | `waiting` |
| `{"type":"reset"}` | 膨らみ・順位をすべて消し、待機に戻す（次のラウンド） | いつでも |

- 受け付けない段階で届いた操作は無視する。

### 表示（ブラウザ）

- Node-RED Dashboard は使わず、`http in` ノードで配信する **自作HTML** ＋ `websocket out` で描画する（風船の演出の自由度のため）。
- 作り込み候補:
  - 接続待ち画面（接続済みの子機一覧）
  - 3・2・1 カウントダウン
  - 10人分の風船のリアルタイム表示
  - 割れる演出、順位表
  - 複数ラウンド制
  - 通信が途切れた子機の表示

## ゲームのルール（親機側の処理）

ゲームの判定はすべて親機側（Node-RED）で行い、子機は圧力を送り続けるだけにする。

### 画面

- 画面を **5列 × 2段の10マス** に分割し、1人1マスを割り当てる。
- 各マスには **名前・風船（色）** を表示する。
- 参加者が10人未満のときは、接続している子機の分だけ表示する。

### ゲームの流れ

1. **待機**: 接続済みの子機を画面に表示する。この間に吹いても風船は膨らまない。
2. **スタート**: 講師がブラウザ画面の **スタートボタン** を押す → 3・2・1 のカウントダウン。
3. **計測**: カウントダウン終了と同時に、受信した圧力の足し込みを始める。
4. **破裂**: 足し込んだ値が **しきい値** を超えた人の風船が割れる。割れた順に順位を付ける。
5. **終了**: **5位まで決まる** か、**制限時間** になったら終了し、順位表を表示する。

### 風船の膨らみの計算

風船の大きさは、**吹いた強さ × 吹いた時間** の合計で決まる。

```
膨らみ += max(圧力 - 不感帯, 0) × 前回受信からの経過時間[秒]
```

- **経過時間を掛ける理由**: 子機の送信回数は 1秒に10〜20回でばらつく。受信値をそのまま足すと、送信回数の多い子機が有利になるため。
- **不感帯を引く理由**: 吹いていないときの小さなノイズが積み重なって、勝手に膨らむのを防ぐため。
- **マイナスの値**（吸ったときなど）は 0 として扱う。
- 吹くのを止めても風船は **しぼまない**（大きさを保つ）。

### 割れ判定・順位

- 膨らみが **しきい値** を超えたら破裂。しきい値は全員共通。
- 割れた順に 1位、2位…とする。**5位** まで決まったらゲーム終了。
- 同時に割れた場合は、Node-RED に先に届いたほうを上位にする。
- 制限時間内に割れなかった人は順位なし。

### 当日調整するパラメータ

すべて親機側（Node-RED）で一括変更できるようにする。具体的な値は実機検証のあとで決める。

| パラメータ | 内容 | 値 |
|---|---|---|
| 不感帯 | これ以下の圧力は 0 とみなす [kPa] | 未定 |
| しきい値 | 膨らみがこれを超えたら破裂 [kPa·秒] | 未定 |
| 制限時間 | ゲームを打ち切る時間 [秒] | 未定（例: 60秒） |
| 順位の人数 | 何位まで決まったら終了するか | 5 |

## ハードウェア

### M5Stack CoreS3

| 項目 | 値 |
|---|---|
| PlatformIO board | `m5stack-cores3` |
| framework | `arduino` |
| ライブラリ | `m5stack/M5Unified` |
| シリアル速度 | `monitor_speed = 115200`（コード内の `Serial.begin()` と **必ず合わせる**） |
| USB | ESP32-S3 内蔵USB（USB CDC）で接続するため、通常は **ドライバ不要** |

### Unit Tube Pressure（チューブ型空気圧センサユニット, SKU: U130）

| 項目 | 値 |
|---|---|
| センサー | MCP-H10-B200KPPN |
| 測定範囲 | -100〜200 kPa（ゲージ圧） |
| 出力 | 0.1〜3.1 V のリニア出力、精度 ±1.5 kPa |
| 電源・接続 | 5V、**PORT.B** に接続。HY2.0-4P の **白線がアナログ出力**（黄線は NC） |
| 換算式 | `P[kPa] = 100 * Vout[V] - 110` |
| 無圧時の出力 | 約 1.1 V |

**読み取りの方針**

- 人が吹く圧力は数〜十数 kPa 程度で、測定範囲のごく一部しか使わない。そのため:
  - **起動時に無圧の値を平均してゼロ点にし、差分を使う**
  - 読み取りは複数回の平均でノイズを抑える
  - 吹いていないのに膨らまないよう、**不感帯（しきい値）は親機側で設ける**

> ⚠️ 実際に吹いたときの値の変化量・ノイズは **実機で未確認**。1個で検証してから10個購入する予定。

## 開発ルール

- **`main` は常に動く状態に保つ。** 作業はブランチで行い、**PR 経由でマージ** する（詳しくは下の「GitHub の運用ルール」）。
- **秘密情報はコミットしない。** `secrets.h` / `flows_cred.json` は `.gitignore` 済み。代わりに `secrets.example.h` を置く。
- `.pio/` はビルド成果物なのでコミットしない（`.gitignore` 済み）。
- Node-RED のフローは `flows.json` を書き出してコミットする。**同時編集は衝突しやすいので避ける**（担当を1人に決める）。
- 3年生が詰まったときに追いつけるよう、**ステップごとの完成コード** を用意する（フォルダまたはタグ: `step1-hello`, `step2-display` …）。

### GitHub の運用ルール

#### ブランチ

- ブランチは基本 **`develop` から作成** し、**`develop` へマージ** する。
- ブランチ名は `{prefix}/{作業内容(ケバブケース)}` とする。
  - 例: `feature/child-sensor`, `docs/add-github-rules`

| prefix | 用途 |
|---|---|
| `setup` | 新しい技術の追加（ライブラリ導入など） |
| `feature` | 新しい機能の追加 |
| `fix` | システムに関する修正 |
| `style` | 見た目に関する修正 |
| `docs` | ドキュメントの更新 |
| `refactor` | コードの内容に関する修正 |
| `temp` | 一時的なブランチ（マージするかわからないもの） |

#### コミットメッセージ

- 先頭に以下のプレフィックスを付ける。
  - 例: `feat: 圧力センサーの値を画面に表示`

| prefix | 用途 |
|---|---|
| `add` | ファイルの追加等（機能以外の場合） |
| `feat` | 機能の追加 |
| `fix` | コードの修正（機能自体に変更あり） |
| `refactor` | コードの修正（機能自体に変更はなし） |
| `update` | 機能の更新・削除等 |
