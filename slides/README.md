# slides

ハンズオンのスライドの構成をまとめます。スライド本体は Google スライドで作り、ここには構成と方針だけを置きます。

## 進め方の方針

- 子機のコードは**配布して説明する**。3年生がゼロから書くことはしない。
- 各パートでは、配布コードを**ブロックごとに説明**したあと、**少しだけ自分で編集**してもらう（文字・名前・色など）。
- ボタン・タッチのパートは**やらない**（最終的な子機で使わないため）。
- 画面表示のパートも**やらない**（ほかの授業で扱っているため）。`setup()`/`loop()` や画面に出す部分は、センサーのパートで配布コードを説明するときに軽く触れる。
- 通信のパートでは、**MQTT と Node-RED の仕組みも説明する**。

## 全パート共通の型

担当が分かれても見た目と進め方がそろうよう、各パートは次の順で作る。

1. **このパートのゴール**（できあがりの写真を1枚）
2. **説明**（配布コードをブロックごとに。1枚に1ブロック）
3. **やってみよう**（自分で編集するところ）
4. **できたらこうなる**（画面の写真）
5. **詰まったら**（よくあるつまずき。詳しくは付録のトラブル集）

- 区切りごとに、そこまでの完成コードを用意する（追いつき用）。
- コードは大きく載せる。1枚に載せるのは 15行くらいまで。

## コードの配り方（git で配る）

子機のコードは **配布用のリポジトリを git clone** して配る。別の回で扱う git の復習も兼ねる。ただし git は深入りせず、使うコマンドは `clone`・`switch`・`add`・`commit`・`push` の5つだけにする。

### このリポジトリをそのまま配らない理由

- リポジトリが private で、Node-RED・web・開発中のブランチも見えてしまう
- ルートに `platformio.ini` がないので、ルートを開くと PlatformIO がプロジェクトとして認識しない
- 既定のブランチが `develop`（開発中）になっている

### 配布用リポジトリの構成

`handson-2026-m5-child`（名前は仮）を別に作り、**直下を PlatformIO のプロジェクト**にする。clone したフォルダを開けば、そのまま PlatformIO のプロジェクトになる。

```
handson-2026-m5-child/
├── platformio.ini
├── src/main.cpp
├── include/secrets.example.h
└── .gitignore        ← secrets.h を除外
```

パートごとのコードは**ブランチ**で分ける（タグだと `switch` で切り替えられないため）。

| ブランチ | 中身 | 使うパート |
|---|---|---|
| `step1-hello` | シリアルに Hello を出すだけ | 1. PlatformIO |
| `step2-sensor` | 圧力を読んで画面に出す | 2. センサー |
| `step3-mqtt` | Wi-Fi・MQTT で送る（完成版） | 3. 通信 |

- 既定のブランチは `step1-hello` にする（clone した直後がパート1の状態になる）。
- 開発はこれまでどおりこのリポジトリの `child/` で行い、配布用リポジトリには書き出すだけにする（二重に編集しない）。
- 各ステップのコードは、それだけで動く状態にしておく。

### 当日の git の操作

| 場面 | 操作 | 補足 |
|---|---|---|
| パート1の最初 | `git clone <URL>` → フォルダを VS Code で開く | |
| パート2・3の最初 | `git switch step2-sensor` ／ `git switch step3-mqtt` | 遅れた人の追いつきにもそのまま使える |
| パート3で名前・色を変えたあと | `git switch -c student/<名前>` → `git add` → `git commit` → `git push -u origin student/<名前>` | **push は最後のこの1回だけ** |

- **途中のパートでは commit しない。** 次のパートに切り替えると、自分で変えた内容（Hello の文字・`MAX_KPA` など）は元に戻る。それで問題ないことをスライドで伝える。
  - 未保存・未コミットの変更が残っていて `switch` できないときは、`git restore .` で変更を取り消してから切り替える（「詰まったら」に入れる）。
- **自分のブランチは最後に1回だけ切る。** パートごとに切るとマージが必要になり、git に時間を取られるため。
- **マージはしない。** `student/*` ブランチは push して残すだけで、PR も作らない。

### 全員が同じブランチに push しない理由

全員が同じ行（`MY_NAME`・`MY_COLOR`）を書き換えるので、同じブランチに push すると2人目以降が弾かれ、`pull` するとコンフリクトになる。1人1ブランチにすればぶつからない。

- 見せ方の案: 講師が画面上でわざとコンフリクトを起こして見せ、「だからブランチを分ける」と説明する（3年生にはやらせない）。

### `secrets.h` の扱い

- `secrets.h` は `.gitignore` で除外する。「パスワードはコミットしない」の実例として見せる。
- 当日は `secrets.example.h` をコピーして `secrets.h` を作り、講師が示す SSID・パスワード・PC の IP を書いてもらう。

### 講師の準備

- [ ] 配布用リポジトリを作り、`step1-hello`〜`step3-mqtt` のブランチを用意する
- [ ] 3年生に書き込み権限を付ける（push のため）
- [ ] `step*` ブランチにブランチ保護をかけ、直接 push できないようにする
- [ ] 終わったら `student/*` ブランチをまとめて削除する

### 1. PlatformIO の使い方（25分・7枚）

| # | スライド | 内容 |
|---|---|---|
| 1-1 | ゴール | シリアルモニタに「Hello」が出る |
| 1-2 | PlatformIO とは | VS Code でマイコンのプログラムを書いて書き込む道具 |
| 1-3 | Arduino IDE との違い | コードの書き方は同じ。ボード・ライブラリを `platformio.ini` に書けるので、プロジェクトを配れば全員が同じ設定になる |
| 1-4 | 配布プロジェクトを開く | `git clone` → clone したフォルダを VS Code で開く。`src/main.cpp` と `platformio.ini` の場所 |
| 1-5 | ステータスバーの4つのボタン | ビルド・書き込み・シリアルモニタ・クリーン。これだけ覚えればよい |

### 2. センサーを読む（35分・8枚）

| # | スライド | 内容 |
|---|---|---|
| 2-1 | ゴール | 吹くと画面の数値とバーが上がる。`git switch step2-sensor` でこのパートのコードにする |
| 2-2 | 圧力ユニットのしくみ | 空気の圧力を電圧にして出す。電圧 → kPa の換算式 |
| 2-3 | つなぎ方 | **PORT.B** に接続、チューブの差し込み方（写真）。チューブは1人1本 |
| 2-4 | プログラムの全体像 | `setup()`（起動時に1回）と `loop()`（ずっと繰り返す）。`M5.begin()` で画面などが使えるようになる |
| 2-5 | 値を読む | `analogReadMilliVolts()` と、10回読んで平均する理由（ノイズ） |
| 2-6 | ゼロ点 | 起動時に吹かずに測った値を「0」にする理由。起動中は吹かない |
| 2-7 | やってみよう | 書き込んで吹いてみる。バーがいっぱいになる値（`MAX_KPA`）を変えてみる |
| 2-8 | グラフで見る | シリアルプロッタで、吹いたときの波形を見る |

- 画面に数値とバーを出す部分は、「ここで画面に出している」と指す程度にとどめる。

### 3. 通信：MQTT・Node-RED（60分・11枚）

| # | スライド | 内容 |
|---|---|---|
| 3-1 | ゴール | 大画面の待機画面に自分のマスが出て、吹くと圧力バーが動く。`git switch step3-mqtt` でこのパートのコードにする |
| 3-2 | 全体の構成図 | 子機 → Wi-Fi → MQTT ブローカー → Node-RED → ブラウザ（プロジェクター） |
| 3-3 | MQTT とは | 掲示板のたとえ。送る人（publish）・読む人（subscribe）・掲示板（ブローカー） |
| 3-4 | トピック | `handson/balloon/<名前>` に送る。Node-RED は `handson/balloon/+` で全員分を読む |
| 3-5 | 送るデータ（JSON） | `{"id":"ikai","p":3.2}`。名前と圧力だけ。1秒に10〜20回 |
| 3-6 | Node-RED とは | ノードを線でつないで処理をつくる道具。実際のフローを画面に映して見せる |
| 3-7 | このゲームのフロー | ①設定 ②子機のデータを受け取る ③ゲームの進行 ④表示画面の配信。判定はすべてここでしている |
| 3-8 | 子機のコード（通信部分） | Wi-Fi 接続・MQTT 接続・送信をブロックごとに説明。`secrets.h` に接続先を分けている理由 |
| 3-9 | やってみよう | 名前と風船の色を書き換えて書き込む |
| 3-10 | できたらこうなる | 待機画面に自分のマスが出る。出ないときは「詰まったら」へ |
| 3-11 | 自分の設定を GitHub に残す | `git switch -c student/<名前>` → `add` → `commit` → `push`。同じブランチに push しない理由（講師がコンフリクトを見せる） |

- 見せ方の案: Node-RED の debug ノードで、全員のメッセージが流れてくる様子を映すと、MQTT のイメージがつかみやすい。
